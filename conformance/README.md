# `conformance/` — machine-readable Candid conformance suite

**Status: subtyping, coercion and decoding.** Vectors for the field-id hash, type-table
well-formedness, subtyping, coercion and decoding, generated by the Lean model, and a
runner that checks them against `candid` 0.10. The decoding assertions of
[test/](../test/) are vectors too. See [REWRITE.md](../REWRITE.md) for why this exists.

```
vectors/                 the suite: JSON, one vector per line
runners/candid-0.10/     checks the suite against rust/candid
tools/test-did/          translates test/*.test.did for the model
```

```
cd lean && lake exe oracle write ../conformance/vectors        # regenerate
cd lean && lake exe oracle check ../conformance/vectors/*.json # check against the model
cargo run --release --manifest-path conformance/runners/candid-0.10/Cargo.toml \
    -- conformance/vectors/*.json                              # check against 0.10
cargo run --manifest-path conformance/tools/test-did/Cargo.toml \
    -- test/*.test.did > lean/Oracle/TestDid/Data.lean          # after editing test/
```

## What goes here

A conformance suite that a Candid implementation in *any* language can consume,
plus the generator that produces it from the Lean model in [lean/](../lean/).

Eventually replaces [test/](../test/).

## What is wrong with the current suite

[test/](../test/) contains 471 assertions across six files. They are good
assertions — the problem is packaging, not content.

- **It cannot bootstrap.** The format is a bespoke extension of the Candid text
  grammar, so you need a working Candid text parser before you can run test #1.
  Anyone implementing Candid in a new language hits this wall immediately, and
  this is the likeliest reason there is no ecosystem of conformant third-party
  implementations.
- **The only runner is a Rust test**
  ([rust/candid_parser/tests/test_suite.rs](../rust/candid_parser/tests/test_suite.rs)).
- **Parser conformance has zero cases.** [test/README.md](../test/README.md)
  documents `*.good.did` / `*.bad.did`. There are none in the repo.
- **Encoding is not covered**, which the README explicitly disclaims, because the
  binary format is non-canonical.
- **Subtyping is tested only indirectly** through decoding, so a subtype-checker
  bug surfaces only if it also changes a decode outcome.
- **It is not distributable.** Consuming it means cloning this repo and writing a
  parser for a grammar that exists nowhere else.

## Design

**Vectors are data, not a grammar.** A type is written the way the model holds it and
the wire format sends it: a type table and a root. A runner in any language can read
vector #1 with a JSON parser and nothing else -- no `.did` parser, and no field-id hash,
because field ids are written as numbers. Names and ids are indistinguishable at the
type level, so nothing is lost.

**Generated from Lean, and committed.** [lean/Oracle/](../lean/Oracle/) writes every
file in `vectors/`, and CI writes them again and fails on any difference. So a change
to the model arrives with a diff of exactly the answers it changed, and an implementer
gets the suite without a Lean toolchain. Do not edit the files by hand: hand-written
vectors are written in Lean ([lean/Oracle/Handwritten.lean](../lean/Oracle/Handwritten.lean)),
where each expectation is stated independently of the model and checked against it.

| File | Origin | |
|---|---|---|
| `handwritten.json` | written by hand | named for what each shows; can catch the model being wrong |
| `subtype-primitives.json` | generated | every primitive against every primitive |
| `subtype-small.json` | generated | every pair from a universe of small types, including recursive ones |
| `coerce-small.json` | generated | sample values of each type in that universe, coerced at every type in it |
| `decode-small.json` | generated | each of those samples encoded at its own type, and decoded at it |
| `test-did.json` | from `test/*.test.did` | each message an assertion there names, at its types |

The ways a message can be malformed are all in `handwritten.json`, with their bytes
written out by hand: an encoder produces only well-formed messages, and the model's
encoder and decoder must not be able to agree on a mistake.

A generated vector's expectation is the model's answer, so it cannot catch the model
being wrong. It catches another implementation disagreeing with the model, over more
pairs than anyone would write; which side is wrong is the follow-up.

`test-did.json` is in between. Its vectors carry the model's answers, but each comes
from an assertion in `test/` that people wrote, and the oracle fails unless the model
agrees with that assertion's claim -- accepted, rejected, or equal to some value
([lean/Oracle/TestDid.lean](../lean/Oracle/TestDid.lean)). The `.test.did` files stay
the source: [tools/test-did/](tools/test-did/) translates them into Lean with
`candid_parser`, and CI fails if the translation is out of date.

### Format, version 0

```jsonc
{"version":0,"vectors":[
{"id":"...","kind":"hash","name":"Ok","expect":17724},
{"id":"...","kind":"wellformed","type":<type>,"expect":false},
{"id":"...","kind":"subtype","sub":<type>,"sup":<type>,"expect":true},
{"id":"...","kind":"coerce","value":<value>,"from":<type>,"to":<type>,"expect":{"value":<value>}},
{"id":"...","kind":"coerce","value":<value>,"from":<type>,"to":<type>,"expect":"reject"},
{"id":"...","kind":"decode","bytes":"4449444c...","types":<types>,"expect":{"values":[<value>, ...]}},
{"id":"...","kind":"decode","bytes":"4449444c...","types":<types>,"expect":"reject"}
]}
```

The version stays at 0 until the suite is published: before then nothing depends on
the format, so it changes in place.

- **`id`** is unique across the suite and stable: runners key their known divergences
  on it. Hand-written ids describe the case; generated ids are the question asked,
  `<t> <:? <t'>`, in Candid syntax.
- **`hash`**: `expect` is the field-id hash of `name`.
- **`wellformed`**: whether the type is well formed -- every reference resolves, no
  label repeats, a `oneway` function has no results, every method is a function.
- **`subtype`**: whether `sub <: sup`. Both types are well formed, and each has its
  own table: `sub`'s references index `sub`'s table, and `sup`'s index `sup`'s. An
  implementation that takes one environment for both has to merge them.
- **`coerce`**: `value : from ~> v : to`, where `expect` is `{"value": v}`, or
  `"reject"` when no `v` exists and a decoder must fail. Both types are well formed,
  `value` has type `from`, and an expected `v` has type `to`.
- **`decode`**: `bytes`, in lowercase hex, deserialised at `types` -- decoded, then
  coerced as an argument sequence -- are the `values`, one per type, or are rejected.
  `types` is `{"table": [<entry>, ...], "roots": [<slot>, ...]}`: one table, any
  number of types in it. The types are well formed and each expected value has its
  type. The bytes need not be well formed; most of the hand-written ones are not.

A `<type>` is `{"table": [<entry>, ...], "root": <slot>}`. A `<slot>` is a primitive's
name (`"nat"`, `"principal"`, ...) or a table index (`3`). An `<entry>` is a composite,
an object with exactly one key, and never a primitive:

```jsonc
{"opt": <slot>}
{"vec": <slot>}
{"record":  [[<field id>, <slot>], ...]}   // ids are u32, in no particular order
{"variant": [[<field id>, <slot>], ...]}
{"func": {"args": [<slot>, ...], "rets": [<slot>, ...], "annots": ["query", ...]}}
{"service": [["<method name>", <slot>], ...]}
{"future": [<opcode>, "<hex>"]}            // a type this version does not define
```

Annotations are `query`, `oneway` and `composite_query`. A future type is an opcode
below `-24` and the bytes that came with it (`spec/Candid.md`, "Deserialisation of
future types"). Only a decoder meets one, and no vector has one yet; it is in the format
so that every table the model holds can be written.

A `<value>` carries its own constructor, so it can be read without its type. Every
number in it is a string: `nat` and `int` are unbounded, and a JSON number past 2^53
does not survive most parsers. Decimal strings are canonical — no sign on a natural,
no leading zero, no `-0`.

```jsonc
null                          // the value of null, an absent option, and reserved's value
true / false
{"nat": "5"}   {"int": "-5"}  // also nat8 .. nat64, int8 .. int64, in range
{"float32": "3f800000"}       // the IEEE 754 bits: 8 lowercase hex digits, 16 for float64
{"text": "..."}
{"opt": <value>}
{"vec": [<value>, ...]}
{"record": [[<field id>, <value>], ...]}  // ascending ids, one per field of the type
{"variant": [<field id>, <value>]}
{"principal": "<hex>"}  {"service": "<hex>"}  {"func": ["<hex>", "<method>"]}
```

The hex is the principal's bytes, lowercase.

The reference reader rejects unknown keys, kinds and names rather than skip them: once
the suite is published, the version number is how the format changes.

### Runners

A runner reads every file, checks every vector, and exits nonzero on any disagreement
it does not already know about. Known divergences are listed in the runner with the
reason, and a listed one that starts agreeing is also a failure, so a fix cannot land
without its entry being removed.

A runner is a bridge to one implementation, not a second reader. Whether a vector is
valid -- its types well formed, its values of their types -- is the reference reader's
to say: `lake exe oracle check` checks every file, and CI runs it on the same files the
runners read. A runner translates each vector into its implementation's types and
values and asks; a vector it cannot translate fails the run whatever the known list
says, since the list excuses an answer, never a broken question.

[runners/candid-0.10/](runners/candid-0.10/) checks `rust/candid` through its public
API, using `OptReport::Silence`: the special `opt` rule is part of the relation. It
skips `wellformed` vectors, since 0.10 has no function that checks a type table on its
own. It asks a `coerce` vector by encoding the value at `from` and decoding the bytes at
`to`, since 0.10 coerces only while decoding, and compares the result with the expected
value by encoding both at `to`. For values of that type, encoding is one-to-one, so this
compares the values while leaving their representation in `IDLValue` to 0.10. Its own
workspace, not a member of the root one.

A `decode` vector is asked through `IDLArgs::from_bytes_with_types`, and the result
compared by encoding, as for `coerce`. Where 0.10 cannot represent an expected value,
that is reported as a disagreement rather than a broken vector: the question translated,
and the answer is what 0.10 cannot hold.

### Findings

What the runners have found, recorded so that they outlive the run that found them.

- **`candid` 0.10 accepts a non-subtype after a failed `opt` probe.** To tell the
  ordinary `opt` rule from the special one, `subtype.rs` tries `t <: t'` and discards
  the result. On failure it removes only the failed pair from `gamma`, so pairs proved
  *under* that assumption stay, and a later comparison is answered from them.
  `didc check` accepts a breaking upgrade this way. Vector: `record { X; X' } !<:
  record { opt Y; Y' } (...)`. Fixed in `candid` 0.10.39 (#775), which withdraws every
  assumption made since a failed step.
- **`candid` 0.10 compares function annotations as a list.** The spec identifies them
  up to reordering; `query composite_query` and `composite_query query` are different
  types to 0.10. The `.did` grammar accepts both spellings.
- **The spec had no answer for coercing at an infinite option**, `type R = opt R`, where
  its "else goes to `null`" rule made `5 : nat ~> w : R` depend on its own negation. The
  model said `null` and 0.10 rejected the message. `test/construct.test.did` had asserted
  the rejection since #679, so the spec was fixed to match (#778): the coercion is
  undefined, nothing recovers from it, and decoding fails. The model follows. Vector:
  `5 : nat ~> reject : R where R = opt R (undefined)`.
- **The model, not 0.10, had coercion to `opt reserved` wrong.** It answered `null`
  where the spec gives `opt null`, since `5 : nat ~> null : reserved`. Fixed before
  these vectors were committed, and recorded here because a reference model is only
  worth as much as the disagreements that can correct it. Vector: `5 : nat ~> opt null
  : opt reserved`.

- **`candid` 0.10 allows at most one function annotation in a decoded type.**
  `binary_parser.rs` asserts it; the spec writes `T*(<funcann>*)`. Vector: `decode: a
  function type with two annotations`.
- **`candid` 0.10 accepts a `oneway` function type with results from the wire.** The
  spec says the result list must be empty, and the model rejects the message. Vector:
  `decode: oneway function with a result`.
- **`candid` 0.10 bounds a principal at 29 bytes**, the Internet Computer's limit; the
  spec does not. Whether it should is a question about the spec. Vector: `decode: a
  principal of 30 bytes`.
- **The model and 0.10 agree with every assertion of `test/` they can be asked.** All
  447 that are about decoding, including the ones on future types and on lengths that
  overshoot the input. The model needed no special case for any of them.
- **The spec has no subtyping rule for future types.** `test/subtypes.test.did`
  asserts that one is a subtype of `opt empty` and not of `nat`, which the general
  rules give: every type is a subtype of `reserved` and of every option. The model adds
  only that a future type is a subtype of itself, which no decoder can be asked.

### Still to come

- **Encoding**, against the relation rather than fixed bytes. The binary format is
  not canonical -- the spec calls type serialisation "a relation", since an encoder
  chooses its type table -- so an encoding vector is a value and a type, and the
  runner produces bytes for it. They conform when they decode, strictly, to a type
  *equivalent* to the vector's (the same infinite tree, not mutual subtyping, which
  would let an encoder drop optional fields) and to the vector's value. The judge is
  the model (`lake exe oracle`), or an implementation's own decoder and equivalence
  check, once the decode and subtype vectors have vouched for those. A canonical
  encoding profile -- minimised type graph, fixed entry order -- would make the bytes
  comparable, but would require every encoder to produce it for a property no
  decoder needs; it stays possible as an opt-in, and nothing here depends on it. See
  [REWRITE.md §2](../REWRITE.md#2-what-we-are-building).
- **`.did` parsing** -- the `*.good.did` / `*.bad.did` cases that were always
  documented and never written.
- **Resource exhaustion / cost model** as normative.
  [test/spacebomb.test.did](../test/spacebomb.test.did) is a good start; every
  implementation faces the zip-bomb problem and currently invents its own defense.
- **Published as a versioned artifact** -- data crate, npm package, and a tarball on
  GitHub Releases -- rather than a directory reachable only by cloning.

## Migration

All 471 existing assertions must exist as vectors and pass before
[test/](../test/) is deleted. 447 do, in `test-did.json`. The other 24 wait on parts
of the model that do not exist yet: 7 have text on the left, which is a question for
the textual syntax, and the 17 in `spacebomb.test.did` are valid messages a metered
decoder should reject, which is the cost model's.

For now the `.test.did` files stay the source, translated by
[tools/test-did/](tools/test-did/), so `candid_parser`'s own test suite and these
vectors read the same assertions. Whether that form survives `test/` -- as an authoring
front-end that compiles to Lean, readable without the bootstrap dependency -- or the
assertions move into Lean beside the hand-written vectors is not decided.
