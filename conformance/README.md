# `conformance/` — machine-readable Candid conformance suite

**Status: subtyping.** Vectors for the field-id hash, type-table well-formedness and
subtyping, generated by the Lean model, and a runner that checks them against `candid`
0.10. No values, coercion or wire format yet. See [REWRITE.md](../REWRITE.md) for why
this exists.

```
vectors/                 the suite: JSON, one vector per line
runners/candid-0.10/     checks the suite against rust/candid
```

```
cd lean && lake exe oracle write ../conformance/vectors        # regenerate
cd lean && lake exe oracle check ../conformance/vectors/*.json # check against the model
cargo run --release --manifest-path conformance/runners/candid-0.10/Cargo.toml \
    -- conformance/vectors/*.json                              # check against 0.10
```

## What goes here

A conformance suite that a Candid implementation in *any* language can consume,
plus the generator that produces it from the Lean model in [lean/](../lean/).

Eventually replaces [test/](../test/).

## What is wrong with the current suite

[test/](../test/) contains 471 assertions across six files. They are good
assertions — the problem is packaging, not content.

- **It cannot bootstrap.** The format is a bespoke extension of the Candid text
  grammar, so you need a working Candid text parser before you can run test #1.
  Anyone implementing Candid in a new language hits this wall immediately, and
  this is the likeliest reason there is no ecosystem of conformant third-party
  implementations.
- **The only runner is a Rust test**
  ([rust/candid_parser/tests/test_suite.rs](../rust/candid_parser/tests/test_suite.rs)).
- **Parser conformance has zero cases.** [test/README.md](../test/README.md)
  documents `*.good.did` / `*.bad.did`. There are none in the repo.
- **Encoding is not covered**, which the README explicitly disclaims, because the
  binary format is non-canonical.
- **Subtyping is tested only indirectly** through decoding, so a subtype-checker
  bug surfaces only if it also changes a decode outcome.
- **It is not distributable.** Consuming it means cloning this repo and writing a
  parser for a grammar that exists nowhere else.

## Design

**Vectors are data, not a grammar.** A type is written the way the model holds it and
the wire format sends it: a type table and a root. A runner in any language can read
vector #1 with a JSON parser and nothing else -- no `.did` parser, and no field-id hash,
because field ids are written as numbers. Names and ids are indistinguishable at the
type level, so nothing is lost.

**Generated from Lean, and committed.** [lean/Oracle/](../lean/Oracle/) writes every
file in `vectors/`, and CI writes them again and fails on any difference. So a change
to the model arrives with a diff of exactly the answers it changed, and an implementer
gets the suite without a Lean toolchain. Do not edit the files by hand: hand-written
vectors are written in Lean ([lean/Oracle/Handwritten.lean](../lean/Oracle/Handwritten.lean)),
where each expectation is stated independently of the model and checked against it.

| File | Origin | |
|---|---|---|
| `handwritten.json` | written by hand | named for what each shows; can catch the model being wrong |
| `subtype-primitives.json` | generated | every primitive against every primitive |
| `subtype-small.json` | generated | every pair from a universe of small types, including recursive ones |

A generated vector's expectation is the model's answer, so it cannot catch the model
being wrong. It catches another implementation disagreeing with the model, over more
pairs than anyone would write; which side is wrong is the follow-up.

### Format, version 0

```jsonc
{"version":0,"vectors":[
{"id":"...","kind":"hash","name":"Ok","expect":17724},
{"id":"...","kind":"wellformed","type":<type>,"expect":false},
{"id":"...","kind":"subtype","sub":<type>,"sup":<type>,"expect":true}
]}
```

- **`id`** is unique across the suite and stable: runners key their known divergences
  on it. Hand-written ids describe the case; generated ids are the question asked,
  `<t> <:? <t'>`, in Candid syntax.
- **`hash`**: `expect` is the field-id hash of `name`.
- **`wellformed`**: whether the type is well formed -- every reference resolves, no
  label repeats, a `oneway` function has no results, every method is a function.
- **`subtype`**: whether `sub <: sup`. Both types are well formed, and each has its
  own table: `sub`'s references index `sub`'s table, and `sup`'s index `sup`'s. An
  implementation that takes one environment for both has to merge them.

A `<type>` is `{"table": [<entry>, ...], "root": <slot>}`. A `<slot>` is a primitive's
name (`"nat"`, `"principal"`, ...) or a table index (`3`). An `<entry>` is a composite,
an object with exactly one key, and never a primitive:

```jsonc
{"opt": <slot>}
{"vec": <slot>}
{"record":  [[<field id>, <slot>], ...]}   // ids are u32, in no particular order
{"variant": [[<field id>, <slot>], ...]}
{"func": {"args": [<slot>, ...], "rets": [<slot>, ...], "annots": ["query", ...]}}
{"service": [["<method name>", <slot>], ...]}
```

Annotations are `query`, `oneway` and `composite_query`. Readers should reject unknown
keys, kinds and names rather than skip them: the version number is how the format
changes.

### Runners

A runner reads every file, checks every vector, and exits nonzero on any disagreement
it does not already know about. Known divergences are listed in the runner with the
reason, and a listed one that starts agreeing is also a failure, so a fix cannot land
without its entry being removed.

A runner reads as strictly as the reference reader, and a vector it cannot read fails
the run whatever the known list says: the list excuses an answer, never a broken
question. That includes a `subtype` vector whose types are not well formed, which a
runner checks before asking anything -- an implementation would answer it anyway, and
an unresolved reference typically comes back as an error that reads as `!<:`.

[runners/candid-0.10/](runners/candid-0.10/) checks `rust/candid` through its public
API, using `OptReport::Silence`: the special `opt` rule is part of the relation. It
reads `wellformed` vectors but does not ask them, since 0.10 has no function that
checks a type table on its own. Its own workspace, not a member of the root one.

### Findings

What the runners have found, recorded so that they outlive the run that found them.

- **`candid` 0.10 accepts a non-subtype after a failed `opt` probe.** To tell the
  ordinary `opt` rule from the special one, `subtype.rs` tries `t <: t'` and discards
  the result. On failure it removes only the failed pair from `gamma`, so pairs proved
  *under* that assumption stay, and a later comparison is answered from them.
  `didc check` accepts a breaking upgrade this way. Vector: `record { X; X' } !<:
  record { opt Y; Y' } (...)`. Fixed in `candid` 0.10.39 (#775), which withdraws every
  assumption made since a failed step.
- **`candid` 0.10 compares function annotations as a list.** The spec identifies them
  up to reordering; `query composite_query` and `composite_query query` are different
  types to 0.10. The `.did` grammar accepts both spellings.

### Still to come

- **Coercion and decoding**, once the model has `Value` and `coerce`: `wire` plus
  expected type, then a decoded value or a rejection.
- **Encoding**, against a canonical encoding profile -- deterministic type-table
  ordering, no unused entries, shortest-form LEB128. This has to be defined before it
  can be tested; see [REWRITE.md §7](../REWRITE.md#7-open-questions).
- **`.did` parsing** -- the `*.good.did` / `*.bad.did` cases that were always
  documented and never written.
- **Resource exhaustion / cost model** as normative.
  [test/spacebomb.test.did](../test/spacebomb.test.did) is a good start; every
  implementation faces the zip-bomb problem and currently invents its own defense.
- **Published as a versioned artifact** -- data crate, npm package, and a tarball on
  GitHub Releases -- rather than a directory reachable only by cloning.

## Migration

All 471 existing assertions must exist as vectors and pass before
[test/](../test/) is deleted. Most of them are decoding assertions, so converting them
waits on the model's wire format; until then the subtype vectors are what the oracle
runs against. The `.test.did` form may survive as a human authoring front-end that
compiles to JSON -- readability without the bootstrap dependency -- or the assertions
may move into Lean beside the hand-written vectors. Not decided.
